# YouTube 双语字幕 — 设计

日期：2026-10-22 · 对应路线图 P2

## 要解决什么

在 YouTube 看外语视频时，画面下方同时显示原文和译文字幕。译文要准（整段上下文、术语表生效）、要跟得上播放进度，还不能多花钱（不看的部分不翻译）。

## 关键约束（为什么不能「直接去拉字幕」）

- 字幕的原始数据来自 `/api/timedtext`（`fmt=json3`）。2024 年起 YouTube 要求这个请求带上播放器内 BotGuard 生成的 `pot` 令牌，扩展自己拿 `captionTracks[].baseUrl` 去请求很可能拿到空结果。
- 播放器自己请求字幕时会带上令牌，所以**旁听播放器的请求**是唯一稳定的数据来源。
- （2026-10-29 实测补充）播放器的请求地址 = 字幕轨的 `baseUrl` + `pot`、`potc`、`fmt`、客户端信息等参数（自动翻译时再加 `tlang`）。把旁听到的这些参数（去掉 `tlang`）拼到另一条字幕轨的 `baseUrl` 上，同一页面里就能拉到这个视频的任意字幕轨。所以**令牌靠旁听，选哪条轨由我们决定**。

## 方案

```
页面世界（MAIN）                       隔离世界（内容脚本）                    后台
youtube-hook ──postMessage──▶ youtube-subtitles ──translate 消息──▶ translateSegments
 包装 XHR / fetch，只读取               解析 json3 → 字幕条目                     （复用批量协议、
 /api/timedtext 的响应                  按播放进度分批翻译                          缓存、术语表）
                                        在播放器内渲染双语字幕层
```

1. **旁听（MAIN world，`document_start`）**：包装 `XMLHttpRequest` 与 `fetch`，URL 含 `/api/timedtext` 时读取响应文本，用 `window.postMessage` 交给内容脚本。**不修改响应**，播放器行为完全不变；出错时静默跳过。内容脚本可能晚于播放器就绪，所以钩子缓存最近几次捕获的结果，内容脚本发「就绪」后再补发一次。
2. **解析（纯函数，`src/lib/subtitles.ts`）**：
   - 普通字幕：每个 event 就是一条字幕，取 `tStartMs`、`dDurationMs`、`segs[].utf8`。
   - 自动生成字幕（URL 含 `kind=asr`）：逐词滚动显示，直接翻译每一行会碎成半句。把所有词按时间拼起来，在句末标点、停顿超过 1.2 秒、或累计超过约 18 个词时断句，按句子显示和翻译。
   - 过滤 `[Music]`、`(laughs)` 这类环境音标注和 `>>` 换人标记。
   - 字幕本身就是目标语言时，不处理，保留原生字幕。YouTube 自动翻译（`tlang`）的字幕不当原文，见第 6 点。
3. **翻译（复用后台批量翻译）**：字幕条目就是「段落」，走现有的 `translate` 消息，因此缓存、术语表、漏段补翻都直接可用。上下文里注明「这是视频字幕」，并带上视频标题。**按进度翻译**：只翻译当前时间点之后约 2 分钟内的条目（每批最多 25 条），播放、拖动进度条时继续往后补；不看的部分不花钱。
   **上下文**（2026-10-30 补充）：字幕数据一到手就是全片，所以翻译第一句之前全片内容都在手上，分批只是为了省钱，不该让每批变成孤岛。
   - **滑动窗口**：每批带上前 4 条（原文 + 已有译文）和后 3 条原文，放在 user 消息的 `<before>`、`<after>` 里，明确只用于理解、不翻译不输出。这几行不是 `<s>` 片段，不影响批量协议。解决批与批交界处的代词、一句话跨批。
   - **全片预读**：字幕到手后发一次请求，输入整条字幕（最多 40000 字，少于 200 字不预读），输出 2–3 句内容摘要和最多 12 条术语。之后每批带上摘要（`summary`）和命中的术语（`terms`，走术语表通道）。开关沿用 `extractTerms`。
   - **不阻塞**：预读和翻译并行，字幕照常先显示。术语回来后，已翻好的条目如果和术语冲突就回到待翻译状态，按进度重翻（和长文术语同一规则）；发出时还没有术语的批次，返回后同样检查，不会因为模型不用术语而反复重翻。
   - **缓存**：同一句话在不同视频里意思可能不同，字幕的译文缓存按视频隔离（`scope`，计入缓存键）。网页翻译的缓存键不变；字幕的旧缓存自然不再命中，不用提升 `PROMPT_VERSION`。预读结果按字幕内容缓存，同一视频只付一次。
4. **渲染**：字幕层挂在播放器元素（`#movie_player`）里，全屏时也能显示；用统一的 Shadow DOM 挂载（`mountPageUi` 增加锚点参数）。播放时逐帧读 `video.currentTime`，只在当前条目变化时更新 DOM。我们自己的字幕层显示期间，用 `html[data-ptx-subtitles]` 的 CSS 把原生字幕设为不可见（还在页面上，只是看不到），关掉后恢复。字号随播放器高度缩放；控制栏出现时上移，避免遮挡。
5. **开关**：设置项「YouTube 双语字幕」，默认开启。字幕的显示和隐藏跟随播放器自带的 CC 按钮（用户按 `c` 或点 CC 即可开关）；默认**不**自动打开字幕。自动打开会改变用户自己的播放器设置，我们先不这样做。「仅译文」显示方式沿用全局设置。
6. **原文字幕由我们挑，不动播放器**（2026-10-29 改，取代原来「替用户切换字幕轨」的做法）：
   - 为什么：播放器选哪条字幕轨取决于用户的全局字幕语言偏好（`localStorage` 的 `yt-player-caption-sticky-language`）。实测这个偏好是韩语时，只有日语、英语人工字幕的《群青》被显示成「英语 >> 韩语」，我们再把韩语机翻成中文，绕了两道机器翻译。原来的「切换到人工字幕」用的 `setOption` 又会改写这个全局偏好，影响用户之后看的所有视频。
   - 做法：钩子旁听到播放器的字幕请求时，附带字幕轨列表（`getPlayerResponse()` 的 `captionTracks`，含 `baseUrl`）和视频标题、简介。内容脚本按下面的顺序挑原文轨，和播放器加载的不同（或带 `tlang`）时，让钩子用播放器的令牌参数去拉那一条；拉取失败就用播放器加载的那条。播放器显示什么、用户偏好是什么都不变。
   - 视频语音的语言：有自动字幕时就是自动字幕的语言；没有时，看标题和简介像哪条人工字幕的语言（只能区分中日韩俄这类文字系统不同的语言）。语音是目标语言时不翻译。
   - 挑选顺序（都排除目标语言的轨）：语音同语言的人工字幕 → 播放器加载的那条人工字幕（去掉自动翻译）→ 英文人工字幕 → 任意人工字幕 → 语音同语言的自动字幕。音乐视频的自动字幕常把伴奏和唱腔听成乱码，所以人工字幕总是优先；只能用自动字幕时，字幕层显示「自动字幕」标记。
7. **只有自动字幕的音乐视频，用同步歌词当原文**（2026-10-30 补充）：演唱的语音识别基本不可用（《群青》MV 68 条里 49 条是 `ni`、`car` 这样的碎片），自动字幕改不好，只能换来源。
   - 条件：视频分类是 Music（`microformat.playerMicroformatRenderer.category`），原文轨只能用自动字幕，用户没有在字幕菜单里换过轨，设置 `videoLyrics` 打开（默认开）。
   - 查询：从标题和频道名解析歌手、歌名（`Artist「Title」…`、`Artist - Title`，频道名去掉 ` - Topic`、`VEVO`），后台请求 LRCLIB 的 `/api/search`，查不到再用歌手 + 歌名全文搜索。只选带时间轴、文字系统和字幕语言一致的歌词，时长最接近的优先；结果缓存，同一首歌只查一次。
   - 对齐：MV 和专辑版时间轴不同，把自动字幕里还算对的句子和歌词比对，每对相似的句子给出一个时间差投票，3 秒窗口内得票最多的时间差就是偏移（重复的副歌投给错误偏移的票分散，不影响结果）。至少 3 票才算对上；票数不够时，只有歌词和视频时长相差不超过 5 秒才按偏移 0 使用，否则放弃歌词。对不上的时间轴比没有歌词更糟。
   - 流程：查询和对齐完成前不开始翻译（避免为马上被替换的自动字幕付费），字幕层先显示自动字幕。查到就替换这一轨的条目，字幕层显示「歌词」标记；查不到或对不上就继续用自动字幕，全片预读在这之后进行，读到的是最终的原文。
8. **切换视频**：YouTube 是单页应用，切换视频不刷新页面。字幕轨按 `v` 参数记录视频 ID，与当前 URL 的视频 ID 不一致时隐藏；新的 timedtext 到来后再切换。

## 不做 / 边界

- 不做画面 OCR，不支持烧录在画面里的字幕。
- 直播字幕（实时增量）、Shorts、嵌入式播放器（`/embed`）先不做，下一步再看。
- 广告期间不显示（广告不会请求同一视频的字幕）。
- 不在播放器控制栏加按钮：直接沿用 CC 按钮，避免改动 YouTube 的界面。

## 测试

- 单元：json3 解析、自动字幕合句、环境音过滤、按进度挑选待翻译条目。
- E2E：新增 `e2e` 构建模式，只在该模式下让 YouTube 脚本额外匹配 `127.0.0.1`（正式构建的 manifest 不变）。仿 YouTube 的测试页用 canvas 视频流当作时间源，点「CC」时由页面自己用 XHR 请求 mock 服务的 `/api/timedtext`，以此验证旁听、渲染、跟随进度、按进度翻译、CC 开关和隐藏原生字幕。
- 实测：用 deepseek-flash 在真实 YouTube 视频上手动验证一次（YouTube 对无头浏览器可能有限制，结果如实记录）。
