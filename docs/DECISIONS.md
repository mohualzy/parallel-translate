# DECISIONS — 技术决策

格式：决策 → 为什么 → 对用户的影响。被推翻时不删除，标注「已废弃」并链接新决策。

## D1 WXT + TypeScript，而不是零构建的原生 JS

- **为什么**：MV3 内容脚本不能直接 `import` 其他文件，background / content / options 共享代码必须打包；WXT 负责生成 manifest、HMR、同时产出 Chrome 和 Firefox 版本。TS 让消息协议、设置结构在三个运行环境之间有类型约束。
- **影响**：需要 `pnpm install` 和一次构建才能加载扩展；换来的是改代码时类型错误在编译期暴露，而不是在某个网页上静默失败。

## D2 弹窗/设置页用原生 DOM，不用 React/Vue

- **为什么**：两个页面都是表单，状态简单；不引入框架可减少依赖和包体积，代码也更容易读懂。
- **影响**：扩展体积小、弹窗打开快。若设置页复杂到难以维护，再迁移到 Preact。

## D3 统一使用 OpenAI 兼容协议（Chat Completions）

- **为什么**：DeepSeek、通义、Kimi、智谱、硅基流动、OpenRouter、Gemini、Ollama 都提供该协议，一个适配器覆盖绝大多数模型。
- **影响**：用户填 Base URL + Key + 模型名即可接入；预设里提供常用 Base URL，模型名可从 `/models` 拉取，不写死可能过时的模型 ID。

## D4 模型请求只在 background 发出，且用流式

- **为什么**：内容脚本的跨域请求受网页 CORS 限制，且不应接触 Key。MV3 Service Worker 在「fetch 30 秒未收到响应」时会被终止，非流式请求在长批次上容易超时；流式响应几乎立即返回响应头。另外请求进行中定期调用扩展 API 保活。
- **影响**：慢模型（含推理模型）的长批次也不会因 Service Worker 被回收而失败。

## D5 多段合并成一次请求，用 `<s id="N">` 标记分段

- **为什么**：逐段请求延迟高、费用高（system prompt 重复计费），且单句缺少上下文。XML 风格标签比 JSON 更不容易被模型输出破坏（无需转义引号）。缺失段的补翻策略见 D14。
- **影响**：翻译更快、更省钱，上下文更连贯；个别模型偶尔漏段时会自动补翻。

## D6 富文本用编号占位标签保留

- **为什么**：链接、加粗、行内代码直接丢掉会让译文不可点击、代码被误译。把行内元素序列化为 `<gN>…</gN>`（需翻译）和 `<xN>…</xN>`（原样保留），译后按编号克隆原元素重建。标签不平衡或过多时降级为纯文本。
- **影响**：译文里的链接可点击、代码不被翻译；弱模型最多退化成纯文本译文，不会出错乱码。

## D7 对页面 DOM 非破坏性；仅译文模式用 CSS 实现

- **为什么**：移动或包裹 React/Vue 管理的节点会导致框架下一次更新时报错甚至白屏。我们只追加自有元素，隐藏原文用 `font-size:0` + 隐藏子元素，并给译文显式设回字号。
- **影响**：在 SPA 网站上更稳定；代价是少数「段落与块级元素混排」的片段在仅译文模式下仍显示原文。

## D8 缓存放 IndexedDB（background 内），不放 storage.local

- **为什么**：缓存条目多、需要按时间清理；storage.local 适合小配置，不适合大量键值。
- **影响**：重复浏览同一页面秒出译文、不重复计费；可在设置页一键清空。

## D9 API Key 存 storage.local，不存 storage.sync

- **为什么**：sync 会把 Key 同步到所有登录同一账号的浏览器；Key 属于设备级秘密。
- **影响**：换设备需重新填写 Key（或用导出功能并勾选包含 Key）。

## D11 默认不自动翻译短的界面文字

- **为什么**：在 GitHub、Wikipedia 上实测，按钮、标签页、导航链接、徽章的译文最容易撑乱布局，对阅读却几乎没有帮助。判定规则（`looksLikeUIChrome`）：不在 p/h*/td 等行文容器里，不超过 3 个词，并且处在链接/按钮里、整段只是一个链接，或者本身是行内块/flex 子项。
- **影响**：页面更整洁、请求更少（GitHub 首屏段落数 224 → 83）；需要时可以悬停按键单独翻译，或在设置里关闭这一行为。

## D12 悬停翻译在「松开按键」时触发

- **为什么**：按下 Ctrl 时还不知道用户是要按 Ctrl+C、Ctrl+点击，还是单按 Ctrl。等到松开时确认中间没有其他按键或鼠标点击，才算单按。
- **影响**：不会和复制、新标签打开链接等常用操作冲突。

## D10 E2E 用 Playwright 1.60.0 自带的 Chromium

- **为什么**：Chrome 137 起正式版禁止用 `--load-extension` 命令行加载扩展，自动化测试只能用 Chromium；1.60.0 对应本机已缓存的 chromium-1223，免去约 150MB 下载。
- **影响**：`just e2e` 开箱即跑；升级 Playwright 时需要 `pnpm exec playwright install chromium`。

## D13 内容被改写的段落等稳定 1 秒再翻译

- **为什么**：AI 对话、实时日志等页面会逐字改写同一段落，原实现每次变化都重新请求。解决办法是设一个段落稳定窗口。判定「被改写」有两条：原有节点的文本变了；或者动态扫描时，同一容器里的整段被换成了新内容（`textContent =` 这类写法会替换掉文本节点，只靠节点身份发现不了）。
- **影响**：E2E 中一段逐字输出的句子从 6 次请求降到最多 2 次；代价是被改写的段落要晚约 1 秒出译文，首次出现的新内容（如无限滚动）不受影响。

## D14 漏段补翻用二分 + 请求预算

- **为什么**：原实现对每个缺失段单独补发请求，模型输出整体乱掉时一批 12 段会变成 12 次额外请求。改为：缺失段对半拆成两组再请求，最多额外 2 次，剩下的标记失败让用户点重试。同一批内相同文本只发送一次。逻辑在 `src/lib/batch.ts`，可单测。
- **影响**：最坏情况的额外费用有上限；漏一两段时仍能自动补齐。

## D15 上下标、时间、图标字体原样保留

- **为什么**：`sup`/`sub` 多是引用角标、化学式、指数，交给模型反而可能被改写；`time` 是相对时间等元信息，翻译收益低；Material Icons 等图标字体靠文字连字显示图标，翻译后图标会变成文字。它们作为原子占位，译文中整体克隆；只有媒体和表单控件因为克隆有副作用而退化为纯文字。
- **影响**：引用角标仍可点击，图标正常显示，送给模型的标签更少。

## D16 目标语言为中文时用中文 prompt，并强调「每段都是完整翻译单元」

- **为什么**：网页里大量是短标题、标签，模型容易回复「请提供更多上下文」，所以为简体中文单独写了中文 prompt。格式约束不变，只调整措辞与语言。修改后 `PROMPT_VERSION` 升到 2，旧缓存不再复用。
- **影响**：短文本译文更稳定，中文输出更自然。

## D17 每个服务可配置额外请求参数（JSON）

- **为什么**：关闭推理模型思考、设置 Ollama `keep_alive` 等参数各家名字不同，无法统一成一个开关。直接让用户填 JSON 合并进请求体；`model`、`messages`、`stream` 不允许覆盖，保存时校验 JSON。
- **影响**：推理模型翻译可以显著提速、降低费用；填错时保存即报错，不会到翻译时才失败。

以下决策来自 2026-10-22 用真实 DeepSeek API 的实测。

## D18 连续两个 `<br>` 视为分段；纯文本片段用空的 `<ptx-t>` 锚点做懒翻译

- **为什么**：paulgraham.com 的文章整篇包在一个行内 `<font>` 里，段落用 `<br><br>` 分隔，结果整篇成了一段：一次请求 46 秒，译文是文末一大块。纯文本片段没有元素可观察，只能观察整个容器，懒翻译也随之失效。现在连续两个 `<br>` 视为分段（包含这种分隔的行内元素按块进入），单个 `<br>` 仍是段内换行；纯文本片段先在其后插入空的 `<ptx-t class="ptx-pending">` 作为观察锚点。
- **影响**：同一页面第一段译文 2.9 秒出现，只翻译滚动到的段落；代价是 `<br><br>` 分段的段落在仅译文模式下不隐藏原文（不是整段容器）。

## D19 `<article>` 内的短链接、短列表项算正文

- **为什么**：GitHub README 的目录列表（`<li><a>Quick Start</a></li>`）被「跳过界面文字」规则当成导航，只有超过 3 个词的一项被翻译，结果不一致。
- **影响**：文章里的目录、短列表都会翻译；`<article>` 之外的导航仍然跳过。

## D20 DeepSeek 预设默认关闭推理，提供可选的真实模型测试

- **为什么**：DeepSeek 当前模型（`deepseek-flash` / `deepseek-v4-pro`）默认开启推理。同一批两段文本实测：默认输出 175 token（其中推理 129），`{"thinking": {"type": "disabled"}}` 后 43 token，协议遵守情况相同。mock 测试证明不了模型是否遵守分段和占位标签协议，所以新增 `just e2e-live`，用真实 API 验证；它使用单独配置，不进 `just e2e`，未设置 `DEEPSEEK_API_KEY` 时跳过。
- **影响**：新建 DeepSeek 服务即为省钱配置；改 prompt 或协议后可以花几分钱跑一次真实验证。

以下是 P1（网页阅读体验补齐，2026-10-22）的决策。

## D21 页面内 UI 统一挂载在 Shadow DOM 里

- **为什么**：划词弹窗、悬浮球、提示框要出现在任意网页上，网页 CSS 不能影响它们，它们的样式也不能泄漏到网页。在 WXT 的 `createShadowRootUi` 外加一层项目约定（`content/ui/mount.ts`）：宿主统一叫 `ptx-ui-*`，段落扫描按前缀忽略；挂在 `<html>` 下，不触发正文的 MutationObserver；同名宿主幂等。
- **影响**：组件在各种网站上外观一致；新增页面内 UI 只需写组件本身。注意 WXT 会在宿主上拦截按键事件，组件内的 Esc 等快捷键要在 shadow root 里监听。

## D22 划词翻译走长连接流式，单词与句子分两种 prompt

- **为什么**：划词是用户主动发起、需要立刻看到结果，所以用 `runtime.connect` 推送增量（关闭弹窗即断开、后台中止请求），不排在网页批量翻译的并发队列后面。单个词适合词典式输出（音标、词性释义、语境含义），句子只要译文；选区所在段落作为语境。划词 prompt 有独立的版本号，调整它不会让网页翻译的缓存失效。
- **影响**：几百毫秒内开始出字。实测中模型曾把单词原样当成音标输出，原因是示例写得不够明确；改成「只写音标」并换用与测试词无关的示例后正常。

## D23 悬浮球：右侧边缘、拖动阈值 6px、按网站隐藏

- **为什么**：不打开弹窗就能开关翻译。用 6px 位移阈值区分点击和拖拽；纵向位置所有网站共用；悬停时提供「在此网站隐藏」。翻译器对外广播开关状态，所以用快捷键、弹窗操作后，悬浮球颜色也会同步。
- **影响**：常用操作只需一次点击；不想看到它的网站可以单独隐藏，或在设置里全局关闭。

## D24 术语表只注入本批出现的条目，并计入缓存键

- **为什么**：术语表可能有几十上百条，全部塞进 prompt 会浪费 token、干扰模型。英文按整词、不区分大小写匹配（避免 cat 命中 category），CJK 等按子串匹配。命中的条目进入该段的缓存键，改了译法不会读到旧缓存。
- **影响**：用户写多少条都不会拖慢普通页面。实测 deepseek-flash 会照用故意指定的冷门译法。

## D25 页面摘要作为上下文，但不计入缓存键

- **为什么**：meta description 能帮模型判断领域（同一个词在医学页和编程页译法不同），成本只有几十个 token。它和标题一样不计入缓存键，好让同一段文字跨页面复用缓存。代价是不同页面的同一段文字可能复用了「别的语境」下的译文，对网页正文来说可以接受。
- **影响**：专业页面用词更贴切；缓存命中率不受影响。

## D26 快捷键沿用同类扩展的习惯，可选命令不设默认键

- **为什么**：Alt+A 翻译、Alt+W 立即翻译整页，与同类扩展的使用习惯一致。「切换仅译文」「学习遮罩」不设默认键，避免和网页、其他扩展冲突（Chrome 每个扩展最多 4 个建议快捷键）。学习遮罩只对当前页生效。
- **影响**：从同类扩展迁移过来不用重新记快捷键；需要的可选命令在 `chrome://extensions/shortcuts` 自己绑定。

## D27 解除截断默认开启，但只在确实裁掉内容时生效

- **为什么**：改页面样式可能影响布局，所以默认开启但条件收紧：译文插入后，容器（及最多 5 层祖先）确实因省略号、行数限制、固定高度溢出时才处理；可滚动容器不处理；在下一帧批量读布局；关闭翻译时复原。
- **影响**：GitHub 提交列表等处的译文能完整显示；个别布局可能被撑高，可在设置里关闭。

## D28 模型原样返回的译文不显示

- **为什么**：实测 GitHub 上作者名被模型原样返回（这是对的），我们却又插入了一遍，变成重复。去掉占位标签、统一空白、大小写、实体后，如果和原文相同，就不插入译文。
- **影响**：人名、产品名、代码等不再重复显示。

## D29 翻译时替换标签页标题

- **为什么**：标题也是页面内容的一部分。开启翻译时把 `document.title` 换成译文，关闭时还原；页面自己改标题（SPA 切换路由）时重新翻译；发给模型的上下文仍用原标题。
- **影响**：多标签页时更容易找到页面；浏览历史里记录的是译文标题。可在设置里关闭。

## D30 Shadow DOM 按组合树遍历；iframe 跟随顶层页面

- **为什么**：Web Components 网站（如新版 Reddit）的正文在 shadow 树里。按组合树遍历：open shadow root 取其子节点、`<slot>` 取分配进来的节点、向上查找时穿过 shadow 边界；shadow root 用 `adoptedStyleSheets` 注入样式，并单独挂 MutationObserver。closed shadow root 读不到，无法支持。iframe：内容脚本在所有 frame 运行，但弹窗、快捷键只和顶层页面通信，顶层页面的开关变化经后台广播给 iframe；小于 120×60 的 iframe（广告、追踪像素）不翻译。
- **影响**：嵌入内容和组件化页面也能翻译，所有 frame 的翻译状态保持一致，不在广告上花钱。

以下是 P2「YouTube 双语字幕」的决策（设计：docs/specs/2026-10-22-youtube-subtitles-design.md）。

## D31 旁听播放器自己的字幕请求，而不是自己拉字幕

- **为什么**：字幕接口 `/api/timedtext` 需要播放器内生成的 `pot` 令牌，扩展自己请求很可能拿到空结果。页面世界（MAIN world）的脚本包装 XHR / fetch，只读取响应、不修改任何返回值，异常一律吞掉；内容脚本晚于播放器就绪时，由钩子补发缓存的结果。
- **影响**：只要播放器能显示字幕，我们就能拿到完整、带时间轴的字幕，播放器行为完全不变。代价是必须打开 CC 才有数据。

## D32 自己渲染原文 + 译文，原生字幕设为不可见；跟随 CC，不自动打开字幕

- **为什么**：只在原生字幕旁边加一行译文，会和逐词滚动的自动字幕互相打架；自己渲染能把自动字幕合成整句、两行排版稳定。字幕层挂在播放器元素里，全屏时也能显示；关掉 CC、切换视频、关闭设置时立即恢复原生字幕。不自动打开字幕，那会改变用户自己的播放器设置。
- **影响**：按 `c` 即开关双语字幕，和原生习惯一致。字幕层不响应鼠标，所以不能在字幕上划词。

## D33 字幕按播放进度分批翻译，并标注「视频字幕」

- **为什么**：一个 20 分钟视频约 300 条字幕。只翻译当前时间往后 2 分钟、往前 5 秒的条目（每批最多 25 条，最多 2 批并发），播放或拖动进度条时继续补；请求上下文注明「这是连续台词」，要求译文口语、简洁。复用网页翻译的批量协议，缓存、术语表、漏段补翻都直接生效。
- **影响**：只看几分钟就关掉的视频，只为看过的部分付费；字幕译文更像人话。

## D34 自动字幕优先换成人工字幕，换不了就标注

> 2026-10-29 由 D70 取代：不再调用 `setOption` 切换播放器的字幕轨（它会改写用户的全局字幕语言偏好），改为扩展自己拉人工字幕当原文。「人工字幕优先」「只有自动字幕时标注」保留。

- **为什么**：实测 YOASOBI《群青》MV 时，播放器默认加载日语自动生成字幕，语音识别把伴奏和唱腔听成了「あの、その、んんん、しらす」，模型照实翻成「那个，这个，嗯嗯嗯，白饭鱼」。源头错了，翻译再准也没用。所以：播放器加载的是自动字幕、而视频另有人工字幕时，替用户切换过去（同语言 → 英文 → 任意；不选目标语言，因为那条原生字幕本身就能看）。每个视频只切一次，用户手动切回自动字幕就不再干预。只有自动字幕时，字幕层标注「自动字幕」。
- **影响**：带官方字幕的视频自动用上更可靠的源；只能用自动字幕时，用户一眼就知道译文为什么可能离谱。代价是会改动播放器当前选中的字幕轨。切换用的是 YouTube 播放器的非公开接口（`getOption / setOption('captions', …)`），哪天接口变了就退化为「只标注、不切换」，不会出错。

## D35 YouTube 自动翻译的字幕：译成目标语言时让位，译成其他语言时当原文

> 2026-10-29 由 D70 取代：自动翻译的字幕不再当原文，扩展改拉未翻译的原文轨；只有拉取失败时才按本条处理。

- **为什么**：原来只要请求带 `tlang`（YouTube 自动翻译），就让位给原生字幕。实测发现：用户的字幕语言偏好可能是英文，于是只有日语自动字幕的视频会被自动翻译成英文，我们的字幕层就什么都不显示。现在统一交给「字幕是否已是目标语言」的检测来判断：译成中文时交给原生字幕；译成其他语言时，当原文再翻译。自动翻译的语言也计入字幕轨标识，开关自动翻译会重新加载。
- **影响**：不会因为 YouTube 的语言偏好而突然没有双语字幕。实测中 YouTube 把日语自动字幕翻成的英文，有时比日语自动字幕本身更接近真实歌词。

## D36 看不见的内容不翻译，折叠容器不展开

- **为什么**：侧栏里一个高度为 0 的折叠分组的空状态提示被翻译了出来。IntersectionObserver 对「被祖先裁剪成零面积、但贴着边」的元素也报告 `isIntersecting`；随后「解除截断」又把高度为 0 的折叠容器当成「被截断」展开了。现在可见面积为 0 的段落不翻译（继续观察，展开后再翻），宽或高接近 0 的容器绝不解除截断。
- **影响**：不会再翻出、撑开页面有意折叠的内容。

## D37 仅译文模式：隐藏原文挤坏排版时，这一段退回双语

- **为什么**：仅译文模式靠容器 `font-size: 0` 隐藏原文。页面若用 em / ch 等相对字号的单位给容器定宽，宽度会跟着归零，译文被挤成一字一行。我们不能也不应逐个修正页面的 CSS（非破坏性原则），所以在渲染后的下一帧检测：容器宽度缩了一半以上、且译文高于 3 行，就对这一段恢复显示原文。
- **影响**：最坏情况是个别段落在仅译文模式下显示成双语，不会再出现竖排乱码。

## D38 仅译文模式下翻译导航、按钮等界面文字（修订 D11）

- **为什么**：D11 跳过短界面文字、控件，是为了防止双语对照把它们撑乱。仅译文模式是在原位置替换文字，不会撑乱布局，用户也明确希望侧栏导航被翻译。所以仅译文模式下：短界面文字照常翻译；`<button>` 和按钮类角色当普通容器进入，文字在按钮内部替换，按钮照常可点。双语对照模式保持 D11 的行为。切换显示方式时重新扫描页面。
- **影响**：控制台、后台这类导航密集的页面，在仅译文模式下基本全部是中文；双语对照模式下仍然整洁。

以下决策来自输入框翻译（2026-10-23）。

## D39 输入框翻译用独立的目标语言、独立的 prompt，不带术语表

- **为什么**：网页翻译是「外文 → 母语」，输入框翻译是反方向（自己写中文，发出去英文），两者的目标语言不能共用一个设置。术语表是按「外文原文 → 中文译法」写的，用在反方向会把术语译错，所以输入框翻译不注入术语表，也不套用网页翻译的风格要求；prompt 单独要求保留换行、@提及、#话题、URL、表情和 Markdown，因为这些是聊天、评论框里的常见内容。
- **影响**：设置里多一个「输入框翻译成」（默认 English）。想让输入框译文用特定术语，目前只能在原文里直接写英文。

## D40 连按三次空格只认「可信的、非输入法的普通空格」，且只在末尾触发

- **为什么**：中文输入法用空格选词，代码编辑器用空格缩进，都是误触发的高发场景。判定只数 `inputType === 'insertText'` 且内容为空格的可信 `input` 事件（输入法上屏是 `insertCompositionText`，天然不计数），间隔不超过 800ms，并且要求光标在内容末尾、所在行不是纯空白、不在 Monaco / CodeMirror / Ace 里。
- **影响**：正常打字几乎不会误触发；代价是想在文中间触发时必须用 Alt+I（也更符合直觉：只翻选中的那一段）。

## D41 写回按「execCommand → 原生 setter / 合成粘贴 → 剪贴板」逐级退化，每步读回校验

- **为什么**：直接赋 `value` 会绕过 React 的受控值，也不进撤销栈。`document.execCommand('insertText')` 虽已废弃，却是唯一能同时触发 `beforeinput/input`、被各种框架感知、并进入浏览器撤销栈的写法。实测（2026-10-23）：ProseMirror 接受 insertText，多行按段落写入，Ctrl+Z 一次还原；Lexical 必须等选区同步（选中后约 50ms）才接受 insertText，且会丢掉换行，但能正确处理合成的粘贴事件。所以 contenteditable 的多行内容先试粘贴、再试 insertText；单行反过来（普通 contenteditable 不处理合成粘贴）。输入框里 insertText 失败时用原生 setter + `input` 事件，并由扩展记录一次 Ctrl+Z 撤销。全部失败就把译文放进剪贴板。
- **影响**：主流编辑器里 Ctrl+Z 可以撤销翻译；写不进去的输入框也不会让译文丢失。请求期间用户继续输入了，就放弃写回，不会覆盖新内容。

## D42 安装 / 更新时主动给已打开的页面注入内容脚本，发消息失败时再按需注入

- **为什么**：原计划只在用户操作时按需注入，但那样更新扩展后，所有已打开页面上的悬浮球、划词、输入框翻译都是失效的，要先打开弹窗或按快捷键才能恢复；开发时每次 `just build` 重载都会碰到。主动注入的成本和这些页面正常加载时一样（本来就该有脚本）；跳过被丢弃的、还在加载的和浏览器内置页面，逐个注入。按需注入作为兜底（同一标签页 10 秒内只试一次，弹窗每秒查询状态时不会反复去试注入不了的页面）。新增 `scripting` 权限；已有 `<all_urls>` 主机权限，安装时不会多出权限提示。
- **影响**：安装后、更新后都不用刷新页面。正在翻译的页面会接续翻译：段落都在缓存里，几乎瞬间恢复，也不花钱。例外：YouTube 双语字幕依赖 `document_start` 的页面世界钩子，仍需刷新视频页；从本版本之前的版本更新时，旧版脚本没有交接逻辑，可能残留一个失效的悬浮球，刷新一次即可。

以下决策来自常见网站适配（2026-10-23）。

## D43 网站规则只修实测出错的地方，默认用排除、少用白名单，不用哈希类名

- **为什么**：依赖 CSS Modules 带哈希类名的规则，网站每次发版都可能失效，维护成本很高。我们的通用识别已经能处理大多数页面，所以规则只针对实测看到的问题；选择器只用 `data-testid`、`aria-*` 这类稳定属性，单元测试会拦住哈希类名。排除规则失效时，退回通用识别，最坏多翻几段；白名单失效时，整页一段都不翻。所以白名单只用于 Hacker News 这种结构多年不变、正文位置明确的网站。
- **影响**：HN 首页只翻 30 条标题，不再翻 30 行「N points by …」；GitHub 打开代码文件不再逐行发送代码，实测 2559 段降到 2 段。X 只在仅译文模式下有问题（用户名、趋势被意译），用排除规则修正。Reddit 的问题全部来自通用识别（Shadow DOM 里包着 slot 的行内元素、读屏专用的 shadow 宿主），修好通用识别后不需要规则，所有用类似组件库的网站都受益。

## D44 visibility:hidden 的内容不翻译，展开后也不自动补翻

- **为什么**：下拉菜单常用 `visibility:hidden` 收起。它有盒子，也在视口里，IntersectionObserver 照常报告「可见」，结果 GitHub 未登录顶栏的十几项菜单每次都被翻译。现在懒翻译与立即翻译整页都跳过它。代价是：菜单展开时位置没变，IntersectionObserver 不会再通知，展开后的菜单不会自动翻译。
- **影响**：不再为收起的菜单付费。想看展开的菜单的译文，可以悬停按 Ctrl 单独翻译。

## D45 点任一失败提示就重试本页所有失败段落，失败原因直接提示

- **为什么**：翻译失败几乎总是成片发生（限流、网络抖动、余额不足、Key 失效），原因是共同的；逐段重试没有独立价值，失败的段本来就要重翻，一次全部重试和逐个点的费用一样。失败原因原来只藏在悬停提示里，用户分不清该等、该充值还是该改配置，所以在页面顶部直接提示，同一原因 10 秒内只提示一次。
- **影响**：一屏十几段失败，点一下就全部恢复，弹窗里也有同样的按钮。弹窗只统计、只重试顶层页面；iframe 里的失败段落要点 iframe 内的失败提示。

## D46 翻译风格做成按网站选择的 prompt 档案；服务里的自定义要求改为叠加

- **为什么**：技术文档、论文、社交媒体、小说需要的译法差别很大，一段通用风格要求顾此失彼。做法是在同一请求上叠加 prompt 配置：六个档案，只替换 system prompt 里的风格段，分段 / 占位协议不变。
  - **选择方式**：用户为网站指定的 > 页面带 `citation_*` 论文元数据 > 内置主机名映射 > 通用，不额外花请求去让模型判断页面类型。
  - **自定义要求**：服务配置里的自定义要求原来会整个替换默认风格，现在改为叠加在档案之后，否则写过自定义要求的用户就用不上档案。
  - **缓存**：档案计入缓存键。
- **影响**：
  - GitHub、文档站自动按技术文档翻译（API 名保留原文），X、Reddit 更口语，论文页更严谨。
  - 写过自定义要求的用户，提示词会变成「通用风格 + 你的要求」，通常更好；如果原来的要求和通用风格冲突，以后写的为准。
  - 切换风格后，已翻译的页面会按新风格重新请求，产生少量费用。

## D47 长文术语：并行抽取、不阻塞首屏，术语返回后只重翻有冲突的段落

- **为什么**：长文分批翻译，同一术语前后可能译法不同。开启翻译时对长文（正文 ≥ 3000 字，社交媒体风格除外）用一次请求抽取最多 12 个术语，走和用户术语表相同的通道：只注入本批命中的条目，命中的条目计入缓存键。等抽取完成再翻首屏最一致，但首屏会慢 2–4 秒；所以不等，术语返回后检查已经翻好的段落，原文命中术语、译文没用该译法的才重翻。用户术语表优先于 AI 抽取的术语。
- **影响**：
  - 长文前后术语一致，首屏速度不变。
  - 代价有三项：
    - 每篇长文多一次请求（结果按正文缓存，重访不再请求）；
    - 首屏少数段落几秒后可能换一次译文；
    - 模型偶尔会把有固定译法的普通词（task、tool）也列进去，影响很小。
  - 设置里可以关闭。

## D48 侧栏只做单结果的文本翻译，「自动」目标语言覆盖两个方向

- **为什么**：侧栏解决的是「不离开网页翻译任意一段文字」：粘贴邮件、文档看译文，或者把自己写的中文译成英文再复制出去。划词弹窗适合短句，侧栏能常驻、适合长文本和反复修改。多服务 × 多语言并排对比属于 P3「多模型对比」，这次不做。
  - **自动目标语言**：输入不是目标语言（默认中文）就译成目标语言；已经是目标语言就译成「输入框翻译」的目标语言（默认英文）。一个下拉框覆盖两个方向，方向显示在选项里。
  - **服务与风格**：侧栏里切换只影响侧栏，不改全局设置。
  - **选中文字的交接**：右键菜单先同步打开侧栏（`sidePanel.open()` 必须在用户手势里调用），再经 `storage.session` 交接文字，因为侧栏可能还没加载完，消息会丢。
- **影响**：新增 `sidePanel` 权限（安装时不会多出权限提示）和 `Alt+S` 快捷键（与同类扩展可能冲突，需要时自行改键）。Firefox 用 `sidebarAction`，都不支持时在新标签页打开同一页面。

## D49 术语表支持带条件的条目，由模型按语境判断，不开推理

- **为什么**：Apple、Cursor、Python 这类词和普通单词同形，硬规则会把「apple pie」里的 apple 也保留成英文。在条目末尾用括号写适用条件（`Apple（指公司时）`），注入 prompt 时写成「仅当指公司时；否则按语境正常翻译」，让模型自己判断。没有开推理：判断词义是读完整句就能顺手做出的事，真正起作用的是 prompt 允许它判断；而推理会让每批的输出 token 和延迟成倍增加（关闭推理时实测少约 75%）。没有条件的条目仍是硬规则，这样大多数无歧义的术语执行得最稳。缓存键只在条目有条件时才带上条件，已有的缓存不失效。
- **影响**：真实模型实测，「Apple released a new iPhone」保留 Apple，「she ate an apple」译为「苹果」。模型偶尔可能判断错；如果实际用下来不准，再考虑只对命中带条件条目的批次开低强度推理。
- **补充（用户反馈）**：
  - 粘贴即自动翻译；手动输入停顿 0.8 秒后也自动翻译（用户确认接受多出的费用：一段话中间停顿几次就是几次整段请求）。
  - 用三条措施压低浪费：连续打字不触发；输入法组字时不计时；内容没变不重复请求。新请求会中止旧请求。
  - 已有译文时，切换服务 / 风格 / 目标语言自动重翻。

以下决策来自 PDF 双语阅读器（2026-10-24）。

## D50 PDF 用本地 pdf.js 渲染，译文「去字形后写回原位置」，而不是在原文上贴译文框

- **为什么**：
  - **不上传**：把文件交给远程网页处理，本地文件就进入了远程页面。我们把 pdf.js 打包进扩展，文件只在本机解析，发给模型的只有文字片段（硬性规则 7）。代价是扩展体积增加约 4.5 MB。
  - **去字形**：用户要求译文和背景像在同一个图层里。所以渲染时拦下 `fillText`，得到只有背景、图片、线条的底图，再在原段落位置用原文的颜色、字重写译文。拉丁字母、数字优先用 PDF 自己的字体，中文回退到系统字体。
  - **公式 / 代码**：靠原字体名识别（CMMI / CMSY / Courier 等），作为不可拆的原子，翻译时用 `<xN/>` 占位，写回时把原字形按比例画到新位置。
- **影响**：
  - 译文页看起来像 PDF 原生排版，行内公式、代码、英文术语和原文完全一致。原型和真实论文实测见设计文档。
  - **局限**：
    - ~~行内分数的分数线、根号上横线会在清底时去掉~~（D58 已解决）；
    - 引用链接的蓝色变成正文颜色（一块一种颜色）；
    - Type3 字体的页面无法去字形，只显示原文；
    - ~~译文页暂不能选择复制文字~~（D57 已解决）。

## D51 PDF 请求要求译文简洁、不加括注；首次翻译前等待文章术语

- **为什么**：
  - **译文长度**：PDF 的空间是固定的。论文风格要求「关键术语首次出现时括注原文」，实测图中的标签被译成「缩放点积注意力（Scaled Dot-Product Attention）」，比原文长一倍，只能缩到很小的字号。所以 PDF 请求加一条上下文：不加括注、解释，用简洁的说法。网页翻译不受影响。
  - **等待术语**：网页翻译时术语抽取不阻塞首屏，事后只重翻有冲突的段落（D47）。PDF 一页是整体绘制的，事后修正会让整页闪一次；打开 PDF 时等几秒也符合预期。所以 PDF 等术语抽取完成（最多 10 秒）再翻第一批。
- **影响**：PDF 译文更紧凑，字号缩小的情况少；长文档前后术语一致；第一页译文出现前多等 2–4 秒。


## D52 PDF 译文按「串」排布：同一栏相邻段落依次往下排，统一字号

- **为什么**：第一版每段译文都从原段落顶部写起、各自缩放字号。中文比英文短三到四成，每段下面都空出一截，段距忽大忽小；每段的缩放又各不相同，字号也忽大忽小（用户实测反馈）。
  - 改为把同一栏里上下相邻、中间没有公式 / 图片 / 保留原文的块连成串，串内译文依次往下排。段距保持原文超出正常行距的那部分（标题前后的空隙还在），省下来的空间集中到串的末尾。
  - 字号以串为单位选择；同一页多行正文的串再取同一个缩放（不低于 0.8），单行的标题、图注标签不参与，免得一个挤的标签拖小整页。
  - 原文段首缩进的段落，译文按中文习惯缩进两字，否则段落挤在一起分不清。
  - 表格单元格不连串，留在原位，免得一格折行把下面整列推离所在的行。
- **影响**：段距均匀、同页字号一致；栏底会出现一段空白（像排版提前结束），而不是散在各段之间；段落位置相对原文会往上挪，双语对照时左右不再逐段齐平。

## D53 PDF 作者姓名不送翻译；颜色不同的短片段（引用、链接）作为原子保留

- **为什么**：
  - **姓名**：作者栏拆开后，姓名单独成段送去翻译，模型会把它音译成中文（「刘嘉伟」），在论文风格下还会加括注原文；音译常常是错的。prompt 里写明「人名不要音译」也不可靠，所以在版面分析里识别：单独一行、由 2–4 个首字母大写的词组成（可用逗号、and 分隔多人）、上下紧挨着字体不同的行（单位）、不含 University 等机构词，就直接保留原文。论文风格同时补上「人名原样保留」，覆盖正文里的人名。
  - **彩色片段**：pdf.js 的文本项不带颜色，链接、引用编号常和前后正文在同一个文本项里。渲染时按字形记录颜色，把文本项按颜色拆开；和正文颜色不同、不超过 4 个词（或带年份的作者-年份式引用）的片段作为原子，翻译时用占位符，写回时画原字形，颜色、字体都不变。引用编号本来也不该翻。
- **影响**：作者栏只译单位、姓名保持原文；引用编号、交叉引用、链接保留原来的颜色。超过 4 个词的彩色句子照常翻译，仍画成正文颜色。识别规则是启发式的：首字母大写的短标签（图里的「User Input」）若恰好上下挨着别的字体，也会被当成姓名保留原文。

## D54 夹在译文之间的行间公式整体平移，跟着上一段走

- **为什么**：串排（D52）后译文往上挪，行间公式还留在原位，文字和公式之间空出一大截（用户实测反馈「文本与公式之间的间隔很奇怪」）。公式由原字形和底图里的矢量线（分数线、根号、矩阵括号）组成，单独搬字形会丢线，所以把「上一段末尾到下一段开头」之间的整条区域当成一张图，从渲染好的画布上整块平移。
  - **条件**：区域里只有保持原样的块（公式、公式编号、栏内的图），都完整落在这一栏内；区域四周在底图上是纯色（没有图片、线条跨过边界）。
  - **串尾**：栏底的公式后面没有下一段，最后一段下方紧接着（3 个字号内逐个相接）的公式也一起平移。
  - **不连的情况**：两段之间直接相连时，空隙里要什么都没有，脚注上方的分隔线、图片会截断串，脚注留在页底；页码不参与平移。
- **影响**：文字和公式的间距与原文一致，省下的空间仍集中在栏底；公式区域整块搬动，图片、线条在边界上时退回原位不动。

## D55 行内粗体、斜体用 `<gN>` 标签交给模型，中文斜体用楷体

- **为什么**：用户希望保留加粗、倾斜。PDF 段落原来只按整段的众数样式画。版面分析时把和段落正文样式不同的片段（按原字体名判断粗体 / 斜体）包进 `<gN>…</gN>`，复用网页翻译已有的占位协议：模型翻译其中的文字并保留标签，写回时按片段的样式画；片段里的英文优先用该片段的原字体。
  - **中文斜体用楷体**：中文没有真正的斜体，浏览器合成的倾斜中文很难看；中文排版里强调、引文的习惯写法是换楷体。整段斜体（作者单位）同样用楷体。
  - **粗体按字体名判断**：pdf.js 认不出 NimbusRomNo9L-Medi 这类粗体，标题原来画成了常规字重。
- **影响**：行内强调、标题粗体、斜体单位都保留下来。模型偶尔丢掉标签时，那一段按正文样式画，不影响译文。

## D56 PDF 译文的中文字体可在阅读器工具栏切换，用本机已安装的字体

- **为什么**：用户想下载几款中文字体随意切换。自动选择（原文衬线用宋体、无衬线用黑体）在 Windows 上落到 SimSun，小字号偏细；原字体栈写的是 `Noto Serif CJK SC`，而 Windows 版 Noto 的族名是 `Noto Serif SC`，装了也用不上。
  - **范围只限 PDF**：PDF 译文画在 canvas 上，中文字体完全由扩展决定；网页译文继承网站自己的字体，要只换中文得往页面注入带 `unicode-range` 的 `@font-face`，目前没有需求。设置键 `pdfCjkFont` 带 pdf 前缀，以后扩到网页另加键，不用迁移。
  - **用系统字体，不导入字体文件**：canvas 按族名就能用已安装的字体，扩展只存一个名字。导入文件要进 IndexedDB、用 `FontFace` 注册，一款中文字体 10–20 MB，还要做导入 / 删除管理，只在不能装字体时才值得。
  - **入口在阅读器工具栏，不在设置页**：看着 PDF 切换才能对比效果。切换时用已有译文重画已渲染的页，不重新渲染 PDF、不重新请求模型。
  - **本机字体列表**：`queryLocalFonts()`，首次要用户点「读取本机字体…」授权，授权后打开阅读器自动列出；只列能显示中文的字体（同一段中文分别以 serif / sans-serif 兜底各画一次，像素相同才算有中文字形）。不支持或被拒绝时用「手动输入…」填族名。
  - **只换中文**：英文、数字仍优先用 PDF 原字体，公式、代码不变；自定义字体后面接自动栈，缺字由它兜底。原文斜体仍用楷体；主字体本身是楷体类（预设楷体或名字含 Kai / 楷）时斜体改用仿宋，否则强调看不出来。
- **影响**：自动模式在装了 Noto Serif SC 的 Windows 上改用它（原来是 SimSun）。字体选择在所有 PDF、所有阅读器标签页之间共用。日文字体（MS Gothic 等）含汉字，也会出现在列表里。

## D57 PDF 译文页：透明文字层负责选中复制，查找栏自建，划词强调画在画布上

- **为什么**：译文画在 canvas 上，选不中、搜不到，用户想复制译文、搜索，并给重点句子加颜色。设计见 [specs/2026-10-24-pdf-text-layer-design.md](specs/2026-10-24-pdf-text-layer-design.md)。
  - **一份文字几何，三处共用**：绘制时产出每块的「显示文本」和每个 token / 文本项的位置。显示文本和断行无关（断行丢掉的行末空格也在里面），换字体、缩放后偏移不变，强调就不会错位。
  - **选中复制用透明文字层**（和 pdf.js 同一思路）：每行一个透明 span，`scaleX` 拉伸到画出来的宽度，块末尾放 `<br>`，复制出来按段落分行。块按阅读顺序（栏优先）排列：版面分析按纵坐标建块，两栏交错，拖选左栏会带上右栏（用户实测反馈）。
  - **查找自建，不用浏览器原生 Ctrl+F**：实测原生查找不能跨绝对定位的行匹配，标题折成两行后「Bilingual Reading」就搜不到；中文在任意字之间换行，「注意力」常被拆开，漏得更多。阅读器接管 Ctrl+F，在显示文本里搜，命中处叠框、显示计数。
  - **强调画在画布上**：所有内容画完后用 `multiply` 叠颜色，白底变色、黑字不变，不用关心和公式平移、原字形的先后顺序；位置和画出来的文字完全一致。DOM 叠层只能按透明文字的近似位置画，词内会偏。
  - **定位**：页码 + 块标识（原文 + 同页序号）+ 显示文本偏移，另存原文字。重新翻译后原位置文字变了就按原文字找，找不到暂不显示、不删除。按 pdf.js 文档指纹存在 `chrome.storage.local`，同一文件从哪打开都一样，不同步、不上传。
- **影响**：可以选中复制译文、Ctrl+F 查找（跨行能找到，范围是看过的页），选中后可加四色高亮或下划线，刷新、换字体后仍在。浏览器菜单里的原生查找仍可用，但跨行的词找不到。只覆盖译文页，原文页暂不能选中。

## D58 行内公式搬动时带上底图里的矢量线；高的公式撑开所在行的行距

- **为什么**：用户读数学多的论文。行内的 $\frac{1}{\sqrt{d_k}}$ 在译文页上只剩「1」和「√dk」：分数线、根号横线是底图上的矢量线，不属于任何字形，清底时被抹掉，搬原子时又只画了字形。高的行内公式按正文行距排，分母压到下一行的字上（1706.03762 第 4 页实测）。
  - **矢量线**：底图不含文字，原子区域里只剩这些线。按文本项估出原子在基线上下的范围（CMEX 根号等大号符号从基线往下挂，单独算），区域里有线就把这块底图按原子同样的缩放、平移画过去；白底用 multiply 叠加，不会盖住旁边的字，彩色底按原样复制。和 D54 平移行间公式是同一个手法。
  - **行距**：排版时量每行原子的上伸、下伸，相邻两行「上一行下伸 + 下一行上伸」放不下时只撑开这一处，其他行保持 1.32 倍；块高随之增加，串排（D52）的装箱照常计算。
- **影响**：行内分数、根号、上划线完整显示，高公式不再压字；有高公式的段落稍长一点，可能让整串字号多缩一档。原子区域里若有别的矢量线（极少，例如恰好穿过的表格线）也会被带过去。

## D59 强调面板：按阅读顺序列出、跳转、导出 Markdown（附原文对照）

- **为什么**：强调原来只能在页面上看，读完一篇论文想整理笔记得逐页翻。工具栏加「强调 N」按钮，右侧面板按页码、页内阅读顺序列出强调，点一条滚过去，可单条删除；导出 Markdown（下载 .md 或复制）。
  - **导出格式**：按页分节；高亮写成 `==…==`（Obsidian 等能直接显示），下划线写 `<u>…</u>`，非黄色注明颜色；同一段里的强调列在一起，后面附这一段的英文原文。强调是译文里的半句话，对不到原文的具体句子，所以附整段，比只给译文更方便核对。
  - **原文从哪来**：绘制时给每块记一份纯文本原文（占位符换回公式字符）。只有本次打开后看过的页才有；没看过的页导出时只有强调文字、没有原文，排序按保存时的偏移。
- **补充**：面板标题栏有「全部清除」，一键清掉这篇文档的全部强调（删了找不回来，先弹窗确认）。
- **影响**：可以一键把一篇论文的强调整理成 Markdown 笔记。原文对照依赖「这一页本次看过」，从头到尾读过一遍的文档最完整。

## D60 原文页也有文字层：可选中复制、可查找原文；强调只在译文页

- **为什么**：想复制英文原句、搜英文术语时，原文页选不中、搜不到，只能换别的阅读器。原文页的文字几何就是「保留原文」块那一套（按原位置取原文、按阅读顺序排），直接复用，不引入 pdf.js 的 TextLayer（另一套样式和定位，和译文页对不齐）。
  - **查找**：查找栏加「译文 / 原文」切换，命中框画在对应那一侧。
  - **强调只在译文页**：原文页上选中时工具条只给「复制」。两边各存一套强调会让面板和导出变复杂，而且同一块在两侧的块标识相同、偏移不同，容易互相串；需要标原文时，导出里已附原文对照。
- **影响**：原文页可以拖选复制、按阅读顺序不跨栏；可以按英文查找。原文页不能加强调。

## D61 自动用双语阅读器打开 PDF：declarativeNetRequest 按响应头重定向，阅读器用动态地址开放

- **为什么**：每次读论文都要先打开 PDF、再点弹窗按钮，多一步。arXiv 的 `/pdf/1706.03762` 没有 `.pdf` 后缀，只能按响应的 `content-type` 判断。
  - **为什么不用 webRequest 监听再跳转**：Chrome 会先打开自带查看器再被换掉（闪一下），历史里多一条 PDF，后退回到 PDF 又被转回阅读器，形成循环。DNR 的 `responseHeaders` 条件（Chrome 128+）可以配合 `redirect`，在浏览器层直接换成阅读器：实测没有闪烁，历史只有「摘要页 → 阅读器」，后退回摘要页。
  - **原地址放在 hash 里**：`regexSubstitution` 不能编码，`pdf.html#<原地址>` 原样保留查询串；请求地址本来不带 `#`。弹窗、右键菜单仍用 `?file=`。
  - **`content-disposition: attachment` 不拦**：那是下载，不是在浏览器里看。
  - **安全**：重定向到扩展页面要求它在 `web_accessible_resources` 里；这会让任意网站能用 iframe 嵌入或跳转到阅读器，让它翻译任意 PDF、消耗用户的 API 额度。设 `use_dynamic_url: true` 后实测：DNR 重定向照常可用，网页嵌入、跳转都被拦（`chrome-error`）。阅读器发现自己在 iframe 里也不加载。
  - **「原文件」按钮**：后台给这个标签页、这个地址加一条会话级放行规则（优先级高于自动打开），再跳过去，用浏览器自带的查看器看；别的标签页不受影响。
  - **默认关**：改变所有 PDF 的打开方式，由用户在设置里打开。
- **影响**：打开开关后，网页上点开的 PDF 直接进阅读器；想看原文件点「原文件」。本地 `file://` PDF 不在 DNR 的作用范围内，仍需拖进阅读器或用弹窗按钮（后由 D67 补上）。新增 `declarativeNetRequest` 权限。

## D62 PDF 记住阅读位置：页码 + 页内比例，按文档指纹存最近 200 篇

- **为什么**：论文常分几次读完，再打开要自己翻回去。
  - **位置用「页码 + 页内比例」**：和缩放、窗口宽度无关；缩放时也用它让视口停在原处（原来缩放后会跳到别处）。
  - **按文档指纹**：同一文件从哪个地址打开都认得。所有文档共用 `pdfPositions` 一个键，只留最近 200 篇，免得越积越多；第 1 页顶部不记。
  - **恢复时机**：要等工具栏渲染完再跳。工具栏在文档流里，渲染完从一行变两行会把页面往下推，先跳就偏了（E2E 实测偏 43 像素）。阅读器自己管位置，`history.scrollRestoration` 设为 `manual`。
- **影响**：再次打开同一篇 PDF 自动回到上次读到的地方；滚动停下 1 秒后保存。

## D63 导出译文 PDF / 双语 PDF：逐页离屏渲染成 JPEG，手写最小 PDF 写入器

- **为什么**：用户想存档、离线读、打印、分享。
  - **图片版**：每页按 2 倍清晰度离屏重新渲染（和当前缩放、视口无关），画好译文和强调后转 JPEG（质量 0.85），立即释放画布。JPEG 直接作为 `DCTDecode` 图片嵌入 PDF，不用解码，写入器只有一百来行、没有依赖。文字不能选中：要能选中得再写一层隐藏文字（字体子集、编码），工作量翻倍，暂不做。
  - **补翻**：没看过的页没有译文，导出前对话框提示剩余页数和费用；补翻走阅读时同一条翻译路径（同一份译文和缓存），导出后再看这些页不用再翻。
  - **两种格式**：仅译文（页面尺寸同原文）；双语并排（左原文、右译文，中间 18 点间隔）。强调一并导出。
  - **后台标签页**：pdf.js 以 `display` 渲染时用 `requestAnimationFrame` 分段，后台标签页里不执行，导出卡住（实测卡在第 2 页）；导出改用 `intent: 'print'`。对话框按钮直接处理点击，不等 `close` 事件（它异步派发，后台标签页里会被拖延）。
- **影响**：一篇 15 页论文导出双语 PDF 约 7 MB、在后台标签页约 1 分钟（含补翻）。导出期间按钮变成「取消导出」，做完当前页停止。

## D64 仅译文模式补全：只占容器一部分的段落、行内公式、按行判断挤窄、CSS 层

- **为什么**：用户在 arXiv HTML 论文（2608.16806v3）上用仅译文模式，标题、目录、贡献列表仍是双语，含公式的段落被切成几截各自双语显示，越往后越多。在真实页面上用 mock 翻译逐项复现，四个根因：
  - **段落只占容器一部分**（目录项 `<li><a>标题</a><ol>子目录</ol></li>`）：原做法只能把整个容器字号归零，容器里还有子目录就不能用，于是退回双语。改为：段落里只有元素（链接、行内标签）时，给这些元素打 `data-ptx-hide-node` 直接隐藏，译文以行内方式顶替原位；有裸文字时不包裹节点就藏不住（硬性规则 2），仍保持双语。
  - **MathML 行内公式**：`<math>` 的计算 display 是 `math`（行间公式是 `block math`），原来不算行内，被当成块级把一段话切成几截。改为按行内算：公式作为占位整体保留，整段一次翻译。
  - **挤窄检测误判**：检测比较的是容器盒子宽度，arXiv 列表项里的 `<p>` 是 `display: inline`，行内元素的盒子只量得到最后一行（实测 779px 的段落量成 32～434px），排得好好的译文被判成挤窄、退回双语。改为比较「隐藏前容器最宽的一行」和「译文最宽的一行」。
  - **CSS 层里的 `!important`**：arXiv 的样式放在 `@layer` 里，标题写了 `font-size: 1.7rem !important`；`!important` 声明里层内的优先于不在层里的，我们的 `font-size: 0 !important` 失效，标题原文藏不住。把仅译文的规则放进 `@layer ptx-hide`：扩展注入的样式表排在页面之前，这个层先声明，`!important` 时优先级最高（实测生效）。
  - 另：两端对齐的段落里，字号为 0 的原文空格仍参与分配每行空余，译文首行前多出 29～45 像素空白。隐藏的容器设 `text-justify: none`，译文设回 `auto`。
- **影响**：arXiv 这类 LaTeXML 页面在仅译文模式下全部只显示译文（真实页面实测：可见范围 64 段译文、双语 0 段），含公式的段落连贯成一段。仍会保持双语的只有「段落只占容器一部分且含裸文字」的情况。对页面的修改多了一种 `data-ptx-hide-node` 属性，仍在硬性规则 2 允许的范围内。

## D65 仅译文的「部分隐藏」只藏安全元素；译文里的链接副本把点击转给原链接

- **为什么**：D64 的修复作用于所有网页，用户要求不能只用论文验证。在 14 个不同类型的真实网站（Wikipedia、GitHub、MDN、Hacker News、BBC、Stack Overflow、Python 文档、React、Cloudflare 博客、Reddit、The Verge、arXiv 摘要页、Kubernetes 文档、Anthropic）上，用 mock 翻译分别跑改动前（git worktree 构建）和改动后的版本逐项对比：
  - 双语残留普遍大幅减少（Wikipedia 68→2、The Verge 28→2、Kubernetes 23→0），没有站点出现「有隐藏标记但字号没归零」，横向溢出与改动前完全一致。
  - **退化**：「部分隐藏」把 `<label>` 也藏了。Kubernetes 侧栏分组标题、Wikipedia 语言菜单都是 label，藏起来后 CSS 画的展开三角和点击行为都没了。改为只藏有真实地址的链接和纯排版的行内标签；含 label / button / `[role]` / `[tabindex]` / `[onclick]`，或只靠脚本的链接（空地址、单独的 `#`、`javascript:`）时保持双语，等于回到改动前。
  - **原有问题**：译文里的链接是原链接的浅克隆，没有页面脚本绑定的事件。原链接被藏起来后，单页应用的路由退化成整页跳转，只靠脚本的链接点了没反应。改为普通左键点击副本时转给原元素 `click()`；带修饰键（新标签页打开等）仍按副本的 href 由浏览器处理。
- **影响**：仅译文模式在各类网站上只显示译文的范围更大，菜单、侧栏的展开按钮保持可用；点译文里的链接和点原链接效果一样。GitHub 未登录页、MDN 的顶部导航在 mock 翻译下有横向溢出，改动前后相同；mock 的「【译】」前缀让文字比原文更长，真实译文更短，用户登录状态的 GitHub 实测没有溢出，暂不处理。

## D66 网页划词强调：一次性，用 CSS Custom Highlight API，入口并进划词工具条

- **为什么**：用户想在网页上给原文、译文加高亮和下划线；明确只要当前页面有效，不需要下次打开还能找到（省掉网页内容变化后重新定位这个难题）。
  - **画法**：CSS Custom Highlight API（`CSS.highlights` + `::highlight()`）直接在 Range 上画背景色、下划线，不插元素、不包裹文字，符合硬性规则 2，React / Vue 页面不受干扰。Range 是活的：页面改文字时跟着调整，译文被移除后画在译文上的强调自然消失。不存储，刷新即没。
  - **叠加规则**同 PDF 强调：新的高亮颜色切掉旧颜色的重叠部分（两侧保留），下划线与高亮可以叠加，「清除」只切掉选中的那段。区间运算（相交、相减）在 `content/marks.ts`，用 happy-dom 的 Range 单测。
  - **入口**：把划词翻译的「译」按钮扩展成工具条 `[译] ●●●● U 清除`。强调按钮对任何选区都出现（中文原文、我们插入的译文也行，编辑区除外）；「译」只在原来的条件下出现；「清除」只在选区碰到强调时出现；直接翻译模式下工具条放到选区上方，免得挡住弹窗。设置「选中文字时显示强调按钮」（`pageMarks`，默认开），关掉后回到原来的划词翻译。
- **影响**：选中中文去复制时也会弹出工具条（只有颜色按钮）；不想要可以在设置里关掉。仅译文模式下原文字号为 0，原文上的强调看不到。

## D67 本地 PDF 自动打开：内容脚本报告加载，后台换成阅读器，前进后退时跳过 PDF 那条历史

- **为什么**：D61 只覆盖网页上的 PDF；双击打开、拖进浏览器的本地 PDF（`file://`）仍走浏览器自带的查看器。
  - **DNR、webRequest 都不作用于 `file://`**。试过 `webNavigation.onBeforeNavigate` 里 `tabs.update`：本地文件加载太快，改道前 PDF 已经提交进历史，后退回到它又被转回阅读器，死循环。
  - **页面自己跳不过去**：内容脚本能注入本地 PDF 的外壳文档，但从 `file://` 页面 `location.replace` 到阅读器（静态地址、动态地址都试了）一律被拦成 `chrome-error`。本地文件是不透明来源，`web_accessible_resources` 放行不了它。只能由后台 `tabs.update`，PDF 那条历史因此留着。
  - **跳过那条历史**：只匹配 `file:///*` 的内容脚本 `local-pdf`（`document_start`，`document.contentType` 是 PDF 才处理，不看后缀）告诉后台「加载了」，并带上是不是前进后退来的（Navigation Timing 的 `back_forward`，往返缓存恢复看 `pageshow.persisted`）。后台：新打开就换成阅读器；前进后退到这条历史时，如果阅读器刚显示的就是这个文件（阅读器显示本地 PDF 时登记），说明是从阅读器后退回来的，让页面接着后退，否则接着前进。这个标签页没自动转过这个文件时什么都不做。状态按「标签页 + 地址」存 `storage.session`，`localPdfAction` 是纯逻辑。
  - **权限**：只有用户在扩展详情页打开「允许访问文件网址」，内容脚本才会注入 `file://` 页面；没开时什么都不发生（阅读器本来也读不到文件）。不需要新权限。
  - **「原文件」**：本地文件放行记在同一个状态里（只对这个标签页），不用 DNR 规则。
- **影响**：打开「自动用阅读器打开 PDF」和「允许访问文件网址」后，本地 PDF 也直接进阅读器。代价是浏览器自带的查看器会先闪一下（改道发生在它开始显示之后），前进后退经过时也会闪一下；后退一次回到打开前的页面，和网页 PDF 一样。

## D68 仅译文模式：没有文字的块级图标不打断段落，按钮「文字 + 图标」整段替换

- **为什么**：`just sweep` 在 15 个网站上统计仅译文模式的双语残留，最常见的是按钮：GitHub、React、Anthropic、BBC、The Verge 的导航按钮（Platform、Download、Research…）。结构都是 flex 容器里「裸文字 + 图标」，图标是块级的（`svg` 设了 `display:block`，或外面包一层 `display:flex` 的 span / div）。块级子元素让段落判定为「只占容器一部分」，裸文字不包裹节点就藏不住，只能双语。
  - **改法**：没有文字（svg 的 `<title>` 不算）、不含表单控件和嵌入媒体的块级子元素算「装饰」，不打断段落，按钮回到「整段」，容器字号归零整段隐藏原文。装饰元素打 `data-ptx-keep` 保留显示，属性值是它隐藏前的字号，CSS 用 `attr(data-ptx-keep type(<length>))` 设回：按 `em` 定大小的图标（React 的 `width="1em"`）不会跟着容器缩没。不支持 `attr()` 类型的浏览器（Firefox）上 em 图标会消失，等于原来整段隐藏的效果。
  - 图标两侧都有文字时仍是两段、都不整段隐藏（不合并段落）；图标旁的换行缩进单独成片段，不计入判定。
- **影响**：仅译文模式下导航按钮只显示译文，箭头、放大镜等图标照常显示、可点。

## D69 仅译文模式：label 里只有链接时只藏链接；有看得见的表单控件时不整段藏；译文不输出控件文字

- **为什么**：`just sweep` 报告里剩下的两类问题。
  - **Kubernetes 侧栏**（一页 22 处双语）：分组标题是 `<label><a>Concepts</a></label>` 后接子菜单，D65 为保住画在 label 上的展开三角不藏 label。label 里的文字全在真实链接里时，改成只藏链接、label 留着：三角照常显示、点击照常展开；译文里的链接副本把点击转给原链接，点文字的效果也不变。label 里有裸文字、有别的带文字元素时仍保持双语。Kubernetes 的侧栏链接是块级的，译文里的链接副本带着同样的类名也成了块级，会和三角分成两行；译文行内顶替原文（`ptx-replace`）时，链接副本一律按行内显示。
  - **Python 文档页头的主题下拉框**（改动前就有）：`<label>Theme <select>…</select></label>` 整段隐藏，下拉框跟着被藏；译文里表单控件原来输出它的文字，下拉框的文字是全部选项，页头显示成「Theme Auto Light Dark」。改为：段落里有看得见的表单控件（`display:none` 的 checkbox 不算）时不整段隐藏，保持双语；译文里下拉框、输入框、文本框、选项不输出文字（按钮仍保留文字）。
- **影响**：仅译文模式下 Kubernetes 这类侧栏只显示译文，展开三角可用；带下拉框、输入框的段落双语显示，控件不再消失，译文里也不再出现选项列表。双语模式下译文里同样不再出现选项文字。

## D70 YouTube 字幕：原文轨由扩展挑、自己拉，不动播放器

- **为什么**：用户的全局字幕语言偏好是韩语时，YOASOBI《群青》（只有日语、英语人工字幕）被播放器显示成「英语 >> 韩语」，扩展再把这条 YouTube 机翻的韩语翻成中文，绕了两道机器翻译。偏好存在 `localStorage` 的 `yt-player-caption-sticky-language`，而 D34 用来切人工字幕的 `setOption` 恰好会改写它，影响之后的所有视频。实测发现，播放器的字幕请求地址就是字幕轨的 `baseUrl` 加上 `pot` 令牌等参数；把这些参数（去掉 `tlang`）拼到另一条字幕轨的 `baseUrl` 上，就能拉到这个视频的任意字幕轨。所以：令牌仍靠旁听播放器的请求（D31），原文轨由扩展按视频本身挑（语音同语言的人工字幕 → 播放器加载的那条人工字幕 → 英文 → 任意人工字幕 → 语音同语言的自动字幕；语音语言取自动字幕的语言，没有时看标题和简介），和播放器加载的不同就让页面世界的钩子去拉，拉取失败退回播放器加载的那条。用户观看中在字幕菜单里换了轨（播放器加载的轨变了），就跟随用户选的轨（仍去掉自动翻译）。
- **影响**：双语字幕的原文不再受全局字幕语言偏好和 YouTube 自动翻译左右，日语歌用日语原文直接翻成中文；扩展不再改动播放器的字幕轨和用户的偏好，原生字幕菜单显示什么照旧。代价：没有自动字幕、标题和简介又判断不出语言（拉丁字母语言之间分不清）时，按播放器加载的那条、再按英文挑；YouTube 自动翻译成中文的视频，现在也用原文轨走模型翻译（多一点费用，但译文用的是你配的模型）。

## D71 字幕翻译的上下文：滑动窗口 + 全片预读，译文缓存按视频隔离

- **为什么**：字幕数据一次就拿到全片，分批（D33）只是为了省钱，但每批只带视频标题：批首看不到前文，一句话跨批时两半分开翻，同一个人名、术语前后译法不一，歌词的比喻也容易译得太字面。所以每批带上前 4 条（原文 + 已有译文）和后 3 条原文；字幕到手后再发一次请求通读整条字幕（最多 40000 字，少于 200 字不预读），得到 2–3 句内容摘要和最多 12 条术语，之后每批带上。摘要和术语合在一次请求里，少付一次钱；术语走术语表通道，只注入本批命中的条目。预读不阻塞字幕，第一批通常先于预读翻完，术语回来后重翻冲突条目（规则同 D47），发出时还没有术语的批次返回后只查一次，模型不用术语也不会反复重翻。不一次翻完全片，否则违背 D33：只看几分钟的视频也要付全片的钱。
- **缓存**：字幕的译文现在依赖上下文，同一句话在不同视频里可能意思不同，所以字幕的缓存键加上视频 ID（`scope`）。网页翻译的缓存键不变，D25 对网页正文的取舍仍然成立；因此不用提升 `PROMPT_VERSION`，网页缓存不作废。字幕的旧缓存不再命中，重看以前的视频要重新付一次翻译费。
- **影响**：
  - 字幕的代词、省略、跨批句子和专有名词更准，同一视频内译法一致，歌曲译文能贴着主题。
  - 代价：每个视频多一次预读请求（按字幕内容缓存，同一视频只付一次），每批多几行输入；开头的几条字幕几秒后可能换一次译文；同一句台词换个视频要重新翻译。
  - 沿用设置项 `extractTerms`，关掉后不预读，滑动窗口仍然生效。

## D72 自动字幕里没有字幕语言文字的条目直接丢弃

- **为什么**：YOASOBI《群青》MV 只有日语自动字幕，语音识别把演唱听成了 `ni`、`car`、`bengali`，68 条里 49 条全是拉丁字母。这些条目不是翻译问题，源头就是错的，模型只能如实转述，用户看到的就是胡言乱语，还要付翻译费。日语、中文、韩语、俄语的自动字幕可以靠文字系统判断：一条里完全没有该语言的文字就丢弃，全片预读也看不到它们。拉丁字母语言之间分不清，不处理。
- **影响**：这类视频不再显示乱码，也不再为乱码付费，但丢弃的时段没有字幕，原生字幕同样被隐藏（内容也是同样的乱码）。带日文字符的听错内容仍会保留，所以这一步治标：没有人工字幕的歌，要准确只能换来源。

## D73 只有自动字幕的音乐视频，用 LRCLIB 同步歌词当原文

- **为什么**：演唱的语音识别基本不可用（D72），丢弃乱码只是治标，缺的句子补不回来，留下的也常常听错。这类视频要准确只能换来源。LRCLIB 是免费、不用密钥的同步歌词库，带时间轴，用歌手和歌名就能查，不用为每首歌单独做什么。只在视频分类是 Music、原文轨只能用自动字幕、用户没有手动换轨时才查询。
  - **时间对齐**：MV 和专辑版的时间轴不同，不能直接用。把自动字幕里还算对的句子和歌词比对，每对相似的句子投一票，3 秒窗口内得票最多的时间差就是偏移，重复的副歌不影响结果。至少 3 票才算对上；票数不够时，只有时长相差不超过 5 秒才按偏移 0 使用，否则放弃歌词：对不上的时间轴比没有歌词更糟。
  - **不先翻译**：查询和对齐完成前不开始翻译，否则要为马上被替换的自动字幕付费。全片预读排在这之后，读到的是最终的原文。
  - **隐私**：这是扩展第一次向模型服务之外发请求，所以写进硬性规则 8：只发歌手和歌名，请求在 background 发出，设置项 `videoLyrics` 可以关闭（默认开）。扩展本来就有 `<all_urls>`，不用新增权限。
- **影响**：
  - 只有自动字幕的歌有了准确、完整的原文和译文，字幕层标注「歌词」。2026-10-30 实测 4 个视频（日语 MV 2 首、日语短版 1 首、英语歌词视频 1 首）都查到了；《群青》MV 上，自动字幕较准的 5 个时间点都落在同一句歌词上。
  - 代价：歌名解析不出来、曲库没有的歌仍是自动字幕；现场版、改编版时间轴可能对不上；偏移只有一个，视频中途插入片段时后半段会错位。查到的歌词来自社区提交，本身也可能有错。
  - 同一首歌的不同视频共用歌词缓存，查询失败或查不到时不缓存，之后还会重新查询。
